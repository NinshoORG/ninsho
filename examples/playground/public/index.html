Ninsho protocol explorer

Every button runs the real Ninsho library on this server. You see the real tokens, what gets written to the store, and what happens when someone attacks it.

How to use it: start with section 1, then go in any order. Green means the library did the right thing. Red means an attack got through, which should never happen.

1 · A session from start to finish

Signing in gives two tokens: a short-lived one for requests, and a refresh token that is replaced every time it is used. Click the buttons left to right.

2 · Signed-in devices

“You are signed in on three devices — sign the others out.” A self-contained token cannot do this, because nothing is checked when it is used. Ninsho checks the store on every request, so it can.

3 · Permissions: who may do what

Signing in says who you are. These checks decide what you may do. Each one runs a real Ninsho guard on a real token. Every row says what should happen and what did.

4 · Attacks, and what stops them

Each button is a real attack on the running system.

Reuse an old refresh token

A thief copies a refresh token; you use it first; the thief tries the old one. Click “Refresh (rotate)” in section 1 first.

Change one character of a token

Edit the token slightly and send it.

Use a password-reset link twice

For example a forwarded email, or a mail scanner that opens links.

Ask for two reset links at the same moment

A new reset link must cancel the old one, even when both are requested at the same instant. This test once found a real bug.

5 · Limiting password guesses

Ninsho counts attempts per network address and per account. Per address alone, an attacker spreads guesses over many machines. Per account alone, one person mistyping locks out a whole office. These run the real limiter.

6 · Your browser holds the key

This section runs in your browser. A private key is made here, marked as impossible to export, and never leaves this page. The server only ever sees signatures. Click 1 to 6 in order.

7 · What the bytes mean

Each button makes a real artefact with the library, then labels it field by field: what it is, how big, and why it is there.

8 · Proving a key came from real hardware

A passkey proves someone holds a key. Attestation also proves which hardware made the key, using certificates from the manufacturer. Pick a device type and a case, then run it. Try “with no trust anchors”: the check refuses, because a certificate chain checked against nothing proves nothing.

9 · What is in the store

Everything Ninsho has saved. Paste any token from this page into the box and search: you will not find it, because only a hash of each token is ever saved.

10 · The audit log

Security events in a fixed shape, with no free-text field that could leak a token or a password.
