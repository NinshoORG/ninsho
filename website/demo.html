The demonstration

Ten panels. Every claim, clickable.

One command starts it. Every button runs the shipped library against real keys and real tokens, then prints the store operations and audit events underneath — so you check the claim rather than accept it.

Nothing on the page is a mock, and nothing is a recording.

Why a demo has tests

A demonstration that stopped demonstrating would look identical.

Every panel restates a claim to an audience with no way to check it. So the playground carries 95 tests of its own, run over real HTTP against the running server.

Each panel states in advance what every outcome should be, and prints a verdict over the table. Without that, a guard that quietly stopped guarding would still render as a tidy table — of the wrong answers.

One test exists purely because of how the panels are wired. They name their routes in data-post attributes, so a renamed route breaks a button with no compile-time and no test-time signal — it fails when a visitor clicks it, which is the worst possible moment and the least likely place for anyone to notice.

95 tests over real HTTP · examples/playground/src/playground.test.ts

Read this before deploying it

The playground is not an integration.

It hands out internals over HTTP on purpose — the live keyspace, the store operations behind every request, the audit trail, and each error's detail, which a real deployment never sends to a client.

Showing detail beside the client-facing message is deliberate: seeing what the server knows next to what the caller is told is the clearest way to make that separation concrete. It is also exactly why this must not be deployed as-is.

Copy examples/express-api instead. It is a complete integration meant to be copied, with 100 end-to-end tests over real HTTP.

Give it its own host and its own network · examples/playground/README.md

Try to break it.

That is what it is for. Every panel prints the evidence behind its own claim, which means it can be caught being wrong.
