The number that moves

“15× faster” is only true on some machines.

Opaque verification beats PASETO verification because Ed25519 is genuinely expensive — around 0.12 ms of pure CPU — while an opaque lookup is a hash and a store read. That conclusion holds everywhere it has been measured. The multiple does not.

Machineopaquepasetoratio
i7-8665U · Node 24110,3558,00113.8×
i7-8665U · Node 24 · re-run105,7486,84015.5×
i5-4300U · Node 2217,2672,9225.9×

Both figures fall on the weaker CPU, but not equally: the opaque path loses about 6× while Ed25519 verification loses only about 2.7×. Ed25519 is a tight, cache-friendly OpenSSL routine whose cost tracks clock speed; the opaque path is comparatively more V8 — allocation, map lookups, object shapes — which suffers far more on an older dual-core with a smaller cache.

So the honest claim is between roughly 6× and 15×, depending on the machine. It does not change which default is right. It does change what you should expect on your own hardware.

WebAuthn

Ceremonies happen once per sign-in.

Not per request — which is the comparison that matters. A registration that costs 0.5 ms is irrelevant beside a verification that runs on every authenticated call.

Two rows worth pausing on. RS256 verification is faster than ES256 — RSA verification with a small public exponent is cheap, while P-256 verification is genuinely expensive; the intuition that RSA is “the slow one” comes from signing. And attestation roughly halves registration throughput, which is the price of a chain verified to your roots rather than trusted on sight.

Method

What a benchmark here has to satisfy.

A warm-up phase is discarded so V8's optimiser has settled. Samples come from performance.now(). Percentiles are taken from the sorted sample array rather than estimated. Inputs that an operation consumes — refresh chains, anti-replay tokens — are pre-generated so fixture cost stays out of the measurement.

And the benchmark scripts are type-checked. That sounds like housekeeping and is not: the DPoP suite was calling the verifier without two required options, which at runtime made both freshness checks compare against NaN and never fire. It was timing a verification with two of its checks disabled. Nothing caught it, because nothing compiled the directory.

Re-running both versions back to back moved the figure by 0.1%, so the published numbers stood. The practice did not, which is why it is recorded here rather than quietly fixed.
